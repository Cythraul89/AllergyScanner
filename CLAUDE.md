# AllergyScanner — Developer Guide

> Quick reference for working on this codebase. The reasoning behind the design
> is in [`doc/ARCHITECTURE.md`](doc/ARCHITECTURE.md); what the app must do is in
> [`doc/REQUIREMENTS.md`](doc/REQUIREMENTS.md).

> **Branch policy**: develop on `feature/**`, open PRs against `develop`. Never
> push to `main` without explicit instruction.

> **Current state**: as of 2026-10-01, `flutter create`, `pub get`,
> `build_runner`, `flutter analyze --fatal-infos` and `flutter test` (201
> tests) all pass on Flutter 3.47.1 stable / Dart 3.13.1, Linux host — see
> "Platform traps" below for what broke on the first run and the fixes
> applied. `go_router` 17 and `archive` 4 are exercised by the widget and
> backup tests respectively. `schemaVersion` is now 4 (allergen groups,
> `scans.name`/`shop`/`photoPath`, `settings.appLanguage`,
> `allergen_groups.color`/`criticality`) with three real `onUpgrade` steps
> and migration tests. The app's UI is now localized (English/German,
> `flutter gen-l10n`) — see "Localization" below. Allergen groups can now
> carry an optional color/criticality tag (REQUIREMENTS R7.16,
> ARCHITECTURE §5.18), and the allergy list (groups + terms only) can be
> exported/imported as a standalone, merge-only JSON file independent of
> the full ZIP backup (R7.17, §8.6–§8.8) — see "Platform traps" below for
> the migration pitfall this uncovered. A matched allergen is now highlighted in its
> group's colour wherever it is marked in ingredient text — the scan review
> preview and, newly highlighted, the result view's evaluated text (R7.16).
> `backupFormatVersion` is now 3: the
> full ZIP backup carries allergen groups and each term's `groupId`, so a
> restore no longer flattens every group (R8.9, ARCHITECTURE §5.19), and
> `onUpgrade` now refuses to open a database newer than the build (R4.13)
> instead of silently stamping the older version onto it.
> **Still unverified**: any real Android or iOS device/emulator build (no
> native toolchain has run against this project yet), and therefore
> `mobile_scanner`, `drift_flutter`'s isolate behaviour, and `share_plus`,
> none of which the current test suite exercises — nor is any of the new UI
> (group editing, the marker-gate preview, photo attachment, the language
> picker) manually verified on a real device.

## Generated code

`*.g.dart` is generated by Drift via `build_runner` and is **not committed** —
every CI job regenerates it. Never edit it by hand. Any change under
`core/database/tables/` or `core/database/daos/` requires a `build_runner` run.

`lib/l10n/app_localizations*.dart` is generated by `flutter gen-l10n` from
`lib/l10n/app_en.arb`/`app_de.arb` and is **not committed** either —
`pubspec.yaml`'s `generate: true` (with `l10n.yaml` at the repo root) makes
`flutter pub get`/`test`/`build`/`run` regenerate it automatically, same as
`build_runner` for Drift. Only the `.arb` files are source; never hand-edit
the generated `.dart` files.

Platform folders (`android/`, `ios/`) are **not committed** either. CI scaffolds
each one with `flutter create --platforms=<p> --org <application-id-prefix> .`;
every native change — permissions, `Info.plist` usage descriptions, deployment
targets, `compileSdk` — lives as a patch step in
`.github/workflows/build.yml`. Adding one locally and committing it is a bug. `macos/`, `linux/`, `windows/` and `web/` are
git-ignored too, so an accidental `flutter create` cannot add an unsupported
platform to the repository.

## Architecture in brief

```
UI (ConsumerWidget)
  │ watches read providers, reads action providers
Riverpod providers (Stream / Future / State / Provider<XActions>)
  │ calls
DAOs (Drift, watch* streams, column-scoped writes)   Services (Open Food Facts,
  │ persists                                          ML Kit, backup, WebDAV, log)
SQLite (Drift / NativeDatabase)      flutter_secure_storage (WebDAV password only)

Calculators (pure Dart, static) — TextNormalizer, AllergenMatcher: no I/O at all
```

The scan pipeline exists exactly once, in `features/scan/scan_actions.dart`:
`ScanInput` → (barcode: local product → Open Food Facts) → normalise → match →
persist scan + matches in one transaction → prune history → result view. See
`doc/ARCHITECTURE.md` §4.1.

Providers that **must be overridden** in `ProviderScope` at startup — each is
declared as `throw UnimplementedError('<name> must be overridden')` so a
missing override fails loudly instead of quietly opening a socket in a test:

| Provider | Concrete value |
|---|---|
| `appDatabaseProvider` | `AppDatabase()` |
| `logServiceProvider` | `await LogService.open()` |
| `dioProvider` | `Dio` with 15 s timeouts and the Open Food Facts `User-Agent` |
| `appVersionProvider` | `await AppVersion.load()` (falls back to `unknown`) |
| `openFoodFactsServiceProvider` | `OpenFoodFactsService(dio:, log:)` |
| `translationServiceProvider` | `TranslationService(dio:, log:)` (MyMemory — allergen group name suggestions) |
| `textRecognitionServiceProvider` | `MlKitTextRecognitionService` where capable, else `UnsupportedTextRecognitionService` |
| `backupServiceProvider` | `BackupService(database:, log:, scanPhotos:)` |
| `scanPhotoServiceProvider` | `await ScanPhotoService.open(log:)` |
| `webdavServiceProvider` | `WebdavService(log:)` |
| `secureStorageProvider` | `const FlutterSecureStorage()` |
| `scanCapabilitiesProvider` | `ScanCapabilities.forCurrentPlatform()` (has a default; overridden so router and bootstrap share one instance) |

## Key conventions

- **One normalisation function** — `TextNormalizer.normalize` is called by the
  matcher, by the duplicate check and by the stored `normalizedTerm` column.
  Two implementations that drift apart make terms silently stop matching, which
  in this app looks like "no allergen found". Never inline a second one.
- **`normalizedTerm` is a stored column** — changing the normalisation rules is
  therefore a **migration** that recomputes it for every row, and it can break
  the uniqueness constraint. See the recipe in `CONTRIBUTING.md`.
- **Never say "safe"** — the `noMatch` verdict is worded "no term from your list
  found". The app must not imply a safety assessment
  (`doc/REQUIREMENTS.md` §5.6). Colour never carries the verdict alone.
- **`OffNotFound` ≠ `OffTransient`** — "no such product" and "could not reach
  the server" are separate sealed results. Collapsing them turns an outage into
  a data statement. No `Product?` returns, no `results?.firstOrNull`.
- **Manual overrides are permanent** — a product row with
  `hasManualOverride = true` is never overwritten by a fetch and never counts as
  stale.
- **History rows are snapshots** — `evaluatedText`, `productNameSnapshot` and
  `termSnapshot` are stored so a past verdict survives term deletion and
  product correction, and re-opens with no network. Never recompute a stored
  verdict.
- **Platform capability in one place** — `ScanCapabilities.forCurrentPlatform()`.
  Camera routes are not registered where they cannot work, so no navigation path
  reaches a dead screen. No `Platform.is*` checks in widgets.
- **Calculators are pure** — no I/O, no logging, no `DateTime.now()` inside;
  pass the time in so tests are deterministic.
- **Reactive reads, targeted writes** — UI watches DAO streams; writes are
  column-scoped DAO methods. Never persist
  `save(staleProviderSnapshot.copyWith(...))`.
- **Immutable domain models** — `const` constructor, `final` fields,
  `copyWith`, `Equatable`. Drift `*Row` classes never leave the DAO layer.
- **No credentials outside the key store** — the WebDAV password lives in
  `flutter_secure_storage` only; never in SQLite, a log or a backup archive.
- **Everything logs through `LogService`** — `print` is not used.
- **No `decimal`, no `workmanager`, no notifications** — this app has no money
  and nothing time-triggered. Do not reintroduce them without a documented
  reason.
- **`drift_flutter`, not `sqlite3_flutter_libs`** — the latter is end-of-life
  (`0.6.0+eol`) and does nothing. The connection is
  `driftDatabase(name: 'allergy_scanner')`, which opens on the calling isolate
  as long as `shareAcrossIsolates` is not passed. Do not pass it.
- **The disclaimer is a gate, not a route** — `AdaptiveShell` renders
  `DisclaimerScreen` while `disclaimerAcknowledgedAt` is null. A router
  `redirect` would race the settings stream and bounce the user back.
- **Riverpod 2 is pinned** — `^2.6.1` although 3.x exists; Riverpod 3 moves
  `StateProvider` to a legacy import, so migration is its own task.
- **Reads never write** — `SettingsDao.watch()`/`get()` serve
  `const AppSettings()` while the row is absent; only `ensureDefaults` and the
  setters create it. A read that created the row would make the device-locale
  default impossible.
- **Analyzer strictness** — CI runs `flutter analyze --fatal-infos`. Never use
  `// ignore` to get green.
- **Adaptive layout** — `kDesktopBreakpoint = 600`: `NavigationBar` below,
  `NavigationRail` at or above, extended above ~1200.
- **Every user-facing string goes through `AppLocalizations`** — add the
  English source to `lib/l10n/app_en.arb` and the German translation to
  `app_de.arb` (same key), then `AppLocalizations.of(context)!.yourKey` in
  the widget; `flutter gen-l10n` (or any `pub get`/`test`/`build`) picks it
  up. Log messages and code comments are exempt — only what a user actually
  reads needs a key. A non-widget layer with no `BuildContext` (a service,
  an `Actions` class) must not hardcode user-facing text either: return a
  structured result/sealed reason instead and let the caller that has
  `context` map it to a string — see `BackupFormatProblem` for the pattern,
  and `doc/ARCHITECTURE.md` §5.17 for where this line was deliberately not
  extended (WebDAV's raw exception passthrough).
- **`Formatters`' label methods take `AppLocalizations` as their first
  parameter** — `verdictTitle`, `verdictLabel`, `inputModeLabel`,
  `matchCountLabel`. `dateTime`/`date`/`time`/`dayHeader` do not; they
  follow `Intl.defaultLocale`, which `app.dart`'s `MaterialApp.builder` keeps
  in sync with the resolved locale on every rebuild.

## Platform traps

Append one entry per non-obvious failure that cost debugging time: what broke,
why, and what to do instead.

Confirmed, with the fix that worked — first Linux/Android+iOS-scaffold compile,
2026-08-20 (`flutter create`, `pub get`, `build_runner`, `analyze`, `test` all
green afterwards):

- **`app_database.dart` needs the enum/`ThemeMode` imports directly, not just
  via the table files** — `products_table.dart`/`scans_table.dart` import
  `../../models/enums.dart` and `settings_table.dart` imports `ThemeMode`, but
  Dart imports are not transitive. `app_database.g.dart` is `part of
  'app_database.dart'`, so it shares only `app_database.dart`'s own imports —
  it fails with "Type 'ProductSource'/'ScanInputMode'/'ScanVerdict'/'ThemeMode'
  not found" at `flutter test` time (the analyzer doesn't catch it;
  `analysis_options.yaml` excludes `**/*.g.dart`). Fix: import
  `../models/enums.dart` and `package:flutter/material.dart show ThemeMode` in
  `app_database.dart` itself.
- **A single `IntColumn` primary key with no `.autoIncrement()` is still
  insert-optional** — Drift treats any lone `int` primary key as something
  SQLite could autogenerate as the rowid, so the generated `.insert()`
  constructor takes `Value<int> id`, not a raw `int`, even though the column
  has no default and isn't nullable. Wrap it: `id: const Value(_rowId)`.
- **`package:flutter/material.dart` does not re-export all of `foundation.dart`**
  — only `Brightness` and `UniqueKey` (see `material.dart`'s own `export`
  list). `FlutterExceptionHandler`, `LicenseRegistry` and
  `LicenseEntryWithLineBreaks` need a direct
  `import 'package:flutter/foundation.dart';` in `main.dart`.
- **`file_picker` 12.0.0 dropped the `FilePicker.platform` singleton and
  `FilePickerResult`** — the API is now direct statics returning `PlatformFile`
  values: `FilePicker.pickFile(...)` → `Future<PlatformFile?>`,
  `FilePicker.pickFiles(...)` → `Future<List<PlatformFile>>`. Use
  `picked?.path`, not `picked?.files.single.path`.
- **`dio` 5.11.0 added `DioExceptionType.transformTimeout`** — any exhaustive
  `switch` over `DioExceptionType` written against an older dio needs the new
  case (grouped with the other timeout types here); the analyzer's
  non-exhaustive-switch error is fatal under `--fatal-infos`.
- **Drift widget tests must close the database *inside* the test body, not in
  `tearDown`** — disposing a `StreamProvider` backed by a live `QueryStream`
  schedules an internal `Timer` (drift's own `stream_queries.dart` comment:
  "please call and await Database.close() in your Flutter widget tests!").
  Flutter's post-test invariant check ("A Timer is still pending even after
  the widget tree was disposed") runs *before* the file's `tearDown` hook, so
  closing there is too late — it also corrupts the test run for every test
  after the first failure. Call `await database.close(); await tester.pump();`
  as the last lines of each `testWidgets` body instead.
- **`sqlite3` in unit tests** — confirmed fine: the system `libsqlite3.so.0`
  (via `ldconfig -p`) is enough for `NativeDatabase.memory()`; no extra
  install needed on a plain Ubuntu machine.

Confirmed by CI, 2026-08-20 (Android release build, second attempt — first
attempt fixed the compileSdk error below, second attempt hit R8):

- **`compileSdk = 36` pin went stale — `flutter_secure_storage` now requires
  37** — `build.yml`'s Gradle patch pinned `compileSdk = 36` for
  `flutter_plugin_android_lifecycle`; the installed `flutter_secure_storage`
  version needs `compileSdk` 37 or higher, and CI's `assembleRelease` failed at
  `:app:checkReleaseAarMetadata` with "Dependency ':flutter_secure_storage'
  requires... version 37". Fixed by bumping the patch to `compileSdk = 37`
  (compileSdk is backward-compatible, so this still covers the lifecycle
  plugin's 36 requirement). Confirmed: this specific error is gone from the
  next CI run (it got further, to R8, below).
- **R8 fails on ML Kit's unused per-script recognizer classes** — CI's
  `:app:minifyReleaseWithR8` failed with "Missing class
  com.google.mlkit.vision.text.{chinese,devanagari,japanese,korean}...
  (referenced from ... TextRecognizer.initialize)". `google_mlkit_text_recognition`'s
  core `TextRecognizer` references these optional per-script classes, which
  only exist if their separate sub-packages are added; this app only uses the
  default script, so they're legitimately absent. Fixed by a new `build.yml`
  step appending `-dontwarn com.google.mlkit.vision.text.<script>.**` (chinese,
  devanagari, japanese, korean) to `android/app/proguard-rules.pro` — not yet
  re-verified by a green CI run, and still no local Android SDK on this
  machine to test it directly (the stub at `/usr/lib/android-sdk` has no
  platforms or `sdkmanager`).
- **`mobile_scanner` applies its own Kotlin Gradle Plugin** — CI logs a
  non-fatal warning ("Future versions of Flutter will fail to build if your
  app uses plugins that apply KGP"). Not yet blocking; if a future Flutter
  upgrade turns this fatal, check `mobile_scanner`'s changelog for a
  built-in-Kotlin release before assuming this project's own Gradle config
  broke.

Confirmed, with the fix that worked — adding English/German localization,
2026-09-03 (`flutter pub get`/`gen-l10n`, `analyze`, `test` all green
afterwards):

- **`l10n.yaml`'s `synthetic-package: false` is deprecated, not required** —
  current `flutter gen-l10n` always writes generated output next to the
  `.arb` files (no `package:flutter_gen/...` option any more) and warns
  "no longer has any effect" if the key is present. Leave it out.
- **A hand-built old-schema database in a migration test needs every table
  touched by *any* migration up to the current `schemaVersion`, not just the
  one the test was originally written for** — `migration_test.dart`'s v1
  seed only had `allergen_terms`/`scans` (deliberately narrow, per its own
  comment, for the v1→v2 migration). Adding the v2→v3 `settings.appLanguage`
  column made that same v1 seed fail with "no such table: settings_entries",
  because there is only one live `AppDatabase.schemaVersion` — upgrading
  from v1 now runs *both* migration blocks in one `onUpgrade` call, not just
  the one the test's name suggests. Fixed by adding `settings_entries` (in
  its pre-v3 shape) to the v1 seed too. Any future migration added after
  this one will need the same check against every existing "upgrade from
  an old version" test.
- **`GlobalMaterialLocalizations`' delegate already loads `intl`'s non-English
  date symbol data** — feared `DateFormat('d MMM y', 'de')` would throw
  `LocaleDataException` unless `initializeDateFormatting('de')` was called
  manually first (the usual requirement when using `package:intl` on its
  own). Confirmed empirically instead of assumed: with
  `AppLocalizations.localizationsDelegates` (which includes
  `GlobalMaterialLocalizations.delegate`) already wired into `MaterialApp`,
  `Formatters.dateTime` works immediately once `Intl.defaultLocale` is set to
  `'de'` — no separate initialization call was needed.

Confirmed, with the fix that worked — adding allergen-group color/criticality
and the allergy-list JSON export/import, 2026-10-01 (`build_runner`,
`analyze`, `test` all green afterwards):

- **`Migrator.createTable` builds a table from its *current* Dart
  definition, not a per-version snapshot** — adding `allergen_groups.color`/
  `criticality` (`schemaVersion` 3 → 4) and writing the obvious
  `if (from < 4) { addColumn(color); addColumn(criticality); }` block failed
  a from-v1 upgrade with "duplicate column: color". Cause: this project
  hand-writes `onUpgrade` blocks instead of using `drift_dev`'s
  schema-snapshot tooling (no `build.yaml` scaffold for it, see
  `migration_test.dart`'s own doc comment), so the **existing**
  `if (from < 2)` block's `migrator.createTable(allergenGroups)` — written
  for the v1→v2 migration, long before these columns existed — builds from
  today's table definition and therefore already creates them. A from-v1
  upgrade runs both blocks in the same `onUpgrade` call, so the later block
  then tries to add a column that already exists. Fix: guard the new step to
  `if (from >= 2 && from < 4)`, so it only runs for a v2 or v3 database that
  genuinely lacks the columns, never for one freshly created by the
  `from < 2` step in the same upgrade. Confirmed empirically via
  `migration_test.dart`'s hand-built v2-shaped seed, not assumed. Any future
  column added to a table that an earlier `if (from < N)` block also
  `createTable`s needs this same check — "does an earlier step in this same
  `onUpgrade` already include it?" — not just "add a migration block".
- **`insertOnConflictUpdate` only resolves the *primary key*, not a second
  `UNIQUE` index** — `allergen_terms` has `UNIQUE(normalized_term)` besides
  its uuid primary key, so restoring a backup onto a device that already
  carries the same term under a *different* uuid threw
  `SqliteException(2067): UNIQUE constraint failed` out of the upsert and
  rolled the entire restore back. The upsert looked safe because every
  single-device test restores an archive the same device wrote, where the
  ids match and only the primary key is ever hit — the bug needs two
  devices, i.e. exactly the case a backup exists for. Fix: look the clashing
  row up by `normalizedTerm` and delete it before inserting the archive's
  (history is unaffected — `scan_matches.allergenTermId` is `setNull` and the
  match keeps its `termSnapshot`, R4.7). The general rule: before upserting
  a restored/imported row, check the table for *every* uniqueness constraint,
  not just the one drift's `onConflict` defaults to — and write the test with
  two differently-seeded databases, not a round trip through one.

Expected but **still not yet verified** — no native Android/iOS build has
succeeded yet, only `flutter create`'s scaffolding plus the pure-Dart/Flutter-
host verification loop above. Check these first when a real device/CI build
fails:

- **iOS deployment target** — `google_mlkit_text_recognition` 0.17.1 documents a
  minimum deployment target of 15.5 and Xcode ≥ 15.3. The Flutter template
  generates a lower target, so `build.yml` patches `project.pbxproj`, and the
  `Podfile` too *if one exists* — current Flutter resolves plugins through SPM
  and may not generate one, so that patch is skipped rather than assumed. The
  `project.pbxproj` patch fails the job loudly if its regex matches nothing.
  If `pod install` fails, this is the first thing to check.
- **Android `minSdk` is deliberately not patched** — `build.yml` used to pin
  `minSdk = 21` (ML Kit's documented floor), which *lowered* it below
  Flutter's own `flutter.minSdkVersion` of 24 and below
  `flutter_secure_storage`'s 24. The pin is gone; the Flutter default already
  satisfies every plugin here. Do not reintroduce it — check the plugins'
  floors against `flutter.minSdkVersion` instead.
- **Isolate behaviour of `driftDatabase`** — `drift_flutter` documents that it
  opens on the calling isolate unless `shareAcrossIsolates: true`. If a release
  build crashes on the first query with a missing native library, this is the
  suspect, and the old `sqlite3_flutter_libs` trap has simply moved.
- **`mobile_scanner` 7.x API** — the widget is used as
  `MobileScanner(controller:, onDetect:)` with `controller.stop()` after the
  first hit and `toggleTorch()` for the torch. `errorBuilder` is deliberately
  not used, because its signature changed between major versions.
- **`archive` 4.x and `share_plus` 13.x APIs** — `ArchiveFile.string(...)`,
  `ZipEncoder().encode(archive)`, `ZipDecoder().decodeBytes(...)`,
  `file.readBytes()` (nullable), and `SharePlus.instance.share(ShareParams(...))`.
  All read from the current API docs, none compiled.

## CI pipeline

Three workflows; `build.yml` is the only file containing build steps.

| Workflow | Trigger | Contents |
|---|---|---|
| `build.yml` | `workflow_call` | 2 platforms × (debug, release) + SBOM; inputs `version`, `retention-days`, `application-id-prefix` (default `com.allergyscanner`, passed to `flutter create --org` — the template's `com.example` is store-rejected and immutable after first publish) |
| `ci.yml` | push `main`/`develop`/`feature/**`, PRs | analyse + test → `build.yml` with `<pubspec version>-dev` |
| `release.yml` | tag `v*.*.*` | analyse + test → `build.yml` with the tag version → GitHub Release |

| Platform | Artifact (debug and release) |
|---|---|
| Android | `.apk` (release key when the keystore secrets exist) |
| iOS | `.zip` of `Runner.app`, unsigned — not installable without re-signing |

macOS, Windows and Linux have no jobs: ML Kit supports no desktop platform and
`mobile_scanner` supports only macOS, so a desktop build would ship without one
or both scanning features. Recorded in the README, in `doc/REQUIREMENTS.md` §3
and in `build.yml` — a deliberate deviation from the five-platform house rule,
not an omission.

Release: `git tag v1.0.0 && git push origin v1.0.0`.

## Adding a new Drift table

1. Create `core/database/tables/<name>_table.dart` — extend `Table`,
   `@DataClassName('<Name>Row')`.
2. Add it to `@DriftDatabase(tables: [...])`.
3. Create `core/database/daos/<name>_dao.dart` — `@DriftAccessor`.
4. Add the DAO to `@DriftDatabase(daos: [...])` and as a getter on
   `AppDatabase`.
5. Bump `schemaVersion` and add the `if (from < N)` migration block.
6. Run `dart run build_runner build --delete-conflicting-outputs`.
7. Extend the in-memory DAO test, including foreign-key behaviour.

## External API integrations

| Service | Endpoint | Auth | Notes |
|---|---|---|---|
| Open Food Facts | `GET https://world.openfoodfacts.org/api/v3/product/{barcode}.json?fields=…` | none | Custom `User-Agent` `AllergyScanner/<version> (<contact>)` is **mandatory**. Documented read limit 15 requests/min/IP — the client throttles locally and returns `OffTransient` instead of hammering. Timeouts 15 s. Response envelope of v3 must be confirmed against a live response; the field names in `doc/REQUIREMENTS.md` §6.2 come from the documented data model, not from a captured response. |
| MyMemory | `GET https://api.mymemory.translated.net/get?q=…&langpair=…` | none (keyless; optional `de=<contact>` param for a higher quota) | Allergen group name translation *suggestions* only (REQUIREMENTS §4.1c) — the user reviews every suggestion before it becomes a term. Response shape confirmed against a live request during implementation: `responseData.translatedText`/`.match`, and a `quotaFinished: true` flag (not an HTTP error status) signals the daily quota running out, mapped to `TranslationTransient`. Gated on `remoteLookupEnabled`, same as Open Food Facts. |
| Nextcloud / WebDAV | user-configured base URL | Basic auth; password in `flutter_secure_storage` | Optional. SHA-256 certificate fingerprint pinning for self-signed servers; a mismatch rejects the connection. |
